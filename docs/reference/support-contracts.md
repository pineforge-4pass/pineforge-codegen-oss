## Support contracts

Builtin `array.slice` on a resolved typed array in the script, a function or
method parameter, or a callable-local array opens the view gate and lowers the
script's array storage to typed handles:
shared backing plus half-open windows, with composed offsets for nested slices.
Element writes share bidirectionally; `array.copy` and history freezes detach.
Structural changes detach the affected array, retaining PineForge's existing
resize behavior pending TradingView measurements. Slice-free scripts retain
their previous emitted C++. Slice scripts use eager identity-aware checkpoints
instead of per-variable array journal/history-cache proofs.
Other builtin slice receivers keep the copy with warning PF-W5003 while the
gate stays closed.

`line.all`, `box.all`, `label.all` and `linefill.all` non-var declaration aliases and
single-binder `for … in` loops take ordered snapshots of live handles at each
collection read. Elements keep their drawing type; setters/deletion reach the
live arena. Direct `size`, `first`, `last`, `get` keep their existing live-read
lowering. Structural mutation, collection reassignment/escape, history and
pair-binder iteration retain PF-E5086 pending TV evidence/provenance support;
declaration tails yielding collections as callable/selection values are refused.
`polyline.all` retains PF-E5085 until the engine has a Polyline handle/arena.
`var`/`varip` aliases retain PF-E5086 until a TradingView capture establishes
their lifetime semantics. Whether a later creation in the same bar is visible
through the alias is not yet measured against TradingView.
`tests/test_drawing_collections_alias.py` checks which forms are accepted and
which keep their refusal, and that unrelated emitted C++ stays byte-identical
to the base commit.

Map namespace calls and receiver methods share named-slot argument binding:
positional arguments fill the leading slots, and keywords fill the parameters
with those names, including a functional receiver named `id`. Valid keyword
forms lower as their positional twins; unknown, duplicate, missing and excess
arguments keep the existing map diagnostics. Named receivers retain the map's
value and collection result types, including direct function returns.

User functions and typed methods share a qualifier check after argument
binding. A proven stronger argument qualifier than an explicit `simple` or
`const` parameter raises PF-E2080 at the argument's first token. Qualifier
evidence follows lexical declarations, writes, helper calls and return tails;
unknown expressions keep their existing policy. Qualifier-only overloads and
imported v5 definitions keep their existing handling. Method parsing retains
nonreceiver contracts separately from the linker's overload metadata; linked
method return qualifiers stay unknown. `array.from` keyword elements raise
PF-E2082 at the value.
These checks change no accepted script's emission. The controls in
`tests/test_series_to_simple_parameter_refusal.py` compare complete C++ to
the pinned reference.

User-defined type field defaults containing a call or an authored variable
reference raise PF-E2087 at the default expression's first token, including
within operators and ternaries. Builtin members, builtin variables (for
example `close`) and calculations over literals retain their existing
handling, and a default that reads a variable declared later keeps the
PF-E2075 refusal it had. Constructor arguments and local initializers are
unaffected; `tests/test_field_default_refusal.py` compares accepted controls'
complete C++ to the pinned reference.

A counted `for` whose end or step reads its own counter binds that name to
the counter, including over an outer variable, parameter, block binding or
enclosing counter, and regardless of later global declarations. The start is
evaluated outside that binding; the v6 step is read once with the counter at
its default 0. TradingView measurements establish that direction is fixed
from the start and the first end read at counter 0, then a counter-dependent
end is read again at the start counter before the first continuation test.
Subsequent v6 end reads follow each increment before the next iteration.
An end with no read resolved to this loop's counter gets no additional read
before the first test. Chart and `request.security` helper loops share this
lowering, including
loop values and `break` / `continue`. A non-na v6 step <= 0 after conversion to
the counter's type stops the run with "'step' in loop must be greater than
zero". The float-counter route is v6 only: positive float evidence in the start,
or an unknown start with positive float evidence in the step, selects a float
counter. A division in a loop start keeps its fraction unless it is a constant
division with an exact integer result, which keeps the int route. The float-step
refusal follows TradingView's check type (a division of two ints is int).
A start whose value has positive int evidence
keeps an int counter and its existing end/step narrowing. A v6 loop whose start
has positive int check evidence refuses a float-typed step at the step
expression (`PF-E2079`), with the hint "Use an int step or a float counter."
Without float evidence, counters keep their existing int route.
v5 library bodies keep their int counters and existing step handling. The counter
now wins over an outer same-named variable. An affine chart loop proved endless
(its end is affine in its own counter) is stopped with the loop-time error when
its result reaches an effect. Omission is limited to an unused loop statement
with no calls, whose writes have no readers except self-updates, a break
condition or one further unused variable declaration. Other flagged loops stop
when their result is read in a shape not measured, where TradingView may drop
them. Endless loops in functions, methods and `request.security` still never end
here while TradingView stops them; data-dependent endless loops still hang.

A float-counter loop accumulates its counter by repeated double addition.
TradingView's measured loop-end rule admits a counter whose excess beyond
the end, computed as one double subtraction in the loop's direction, is
strictly below `1e-10`. The named value `kTvFloatStepEnd` is emitted only
when a float-counter loop exists. Measured on TradingView at the 0.3 scale
(counted up to a 9.999e-11 shortfall, not counted from 1.0e-10) and at counter
magnitudes of about 1, 1e3, 1e6 and 1e9; no magnitude-independent constant
is claimed; not a constant TradingView publishes.
A positive infinite step leaves the counter beyond the finite bound after
one iteration; the difference comparison needs no non-finite-step guard.

The additional inexact-step probes and export hashes are recorded in
`tradingview_quantities.json`: `0.0 to 0.3 by 0.1` counts four iterations,
while `0.0 to 2999.9999999999 by 1000.0` counts three. These rows reject
end comparisons that lose the accumulated last iteration or round the end
up before comparing it. Additional recorded counts exercise the measured
end difference in both directions and at the measured counter magnitudes.
Known gaps: a float counter passed to an untyped helper truncates here while
TradingView passes the fractional value (`twice(x)` accumulates 2 here versus 5
on TradingView).
`array.from(x)` can also truncate a float counter through inferred `array<int>`
storage. An untyped parameter can leave the start unknown; a positively float
step then selects a float counter without changing shared parameter inference.
For `f(x)` containing `for v = x to 1.0 by 0.25`, TradingView refuses `f(0)`
with CE10106 and accepts `f(0.0)`. PineForge accepts and runs both with a float
counter because this inference cannot distinguish their call-argument types;
refusing the unknown start would also refuse the valid float-argument call.
Block-local/enclosing-counter bindings, end bounds that change direction during
iteration and stops inside `request.security` have no TradingView tape.
Integer-counter controls are guarded
against previous generated C++ apart from the added step-stop statement.

Per-bar `request.security` timeframes can have a closed set by value:
`codegen/timeframe_values.py` unions selection arms through pure scalar
operators, exact integral string conversions, plain indexed `str.format`
and pure v6 helpers (including inlined libraries). Unknown values,
unproved formatting, persistent timeframe storage and writes keep PF-E3111.
`limits.py` names the inventory and deterministic work bounds. The authored
timeframe still runs at the call; each value has its own registered stream.
Existing literal/input/chart-period arms retain their emitter.
The requested expression's own scalar `var` state uses independent helper
series and once seeds per registered timeframe and helper call. Expanded
arms also admit helper-local `varip` on the historical requested-bar protocol:
new requested bars carry the prior value, repeated evaluations roll back.
Outside persistent bindings use the fixed request's mutable-global replay
independently per registered stream, including aliases and history; bindings
that replay cannot carry retain PF-E3111.
A stateful expanded evaluator cannot fall back to a chart helper call;
conditional helper declarations and unsupported state types keep their gates.
Fixed requests retain their helper-local `varip` refusal.
A numerically int declaration with a fractional `:=` write uses float storage,
including an explicit `int` hint. Reassignments and counters share one numeric
value query and its integral-division proofs. The step check retains the hint
or initializer's type, so a widened int still refuses a float step with PF-E2079.
This covers unambiguous global,
callable, block and loop-body declarations; duplicate storage names, unknown
initializer families and untyped helper parameters remain gaps. Direct
initializers and direct non-quotient numeric-literal writes keep their policy.
Call-site return inference honors the same widening annotation, including
callable-local `var` and `varip`; an `int` return must not narrow their double
storage.
`tests/test_float_reassignment.py` and the measured reassignment fixtures pin
storage, quantities and complete unchanged integer-control C++.

Registry builtins with verified keyword names
(`IntrinsicFunc.keyword_names_verified`) declare their complete keyword set
through their signature parameters. These names are validated before lowering
and again at the shared keyword merge; unknown names report PF-E2027 at the
keyword. Other records keep their existing binding policy. `math.pow`
declares `base, exponent`; both named forms emit the positional expression.
Argument ordering remains the separate PF-E2074 validation.

An aggregate `var` initializer that reads a statement-computed value (directly,
through a user helper, or through another declaration-site `var`) runs at its
declaration under the existing once flag. An earlier reassignment or collection
mutation also requires that route. A history-read UDT opens its first slot with
the typed na handle, then updates that slot at the declaration. Independent
constructors and preamble-safe aliases retain their emission; `varip` takes it
too, and callable-local initialization keeps its existing path.
`tests/test_var_initializer_statement_order.py` pins the order, trades and
persistence against paired script controls.

Numeric `matrix.sum(id1, id2)` returns a detached matrix for either a matrix or numeric scalar RHS; its existing one-argument aggregate lowering is unchanged. Scalar `matrix.diff`/`matrix.mult` also return detached matrices. Typed matrix/vector multiplication and a variable initialized from namespace `array.concat` are refused with the existing unsupported-function diagnostic. Default/index-only matrix row/column insertion fills with element na; omitted submatrix bounds, sort column and array-fill end use the collection dimensions. `tests/test_matrix_arithmetic_overloads.py` compiles and runs these overloads against the paired runtime.

Keyword arguments of the matrix methods and of the checked array methods (`get`, `set`, `insert`, `remove`, `fill`, `slice`, `percentrank`, `first`, `last`, `pop`, `shift`, `sort`, `indexof`, `unshift`) bind to their own parameter slot (`CallVisitor._collection_arg_nodes`; the slots are `MATRIX_METHOD_KWARGS` and `CHECKED_ARRAY_METHOD_KWARGS`, and `row_index` / `col_index` of `add_row` / `add_col` keep binding to `row` / `column`), never shifted left over a gap: a gap before a later argument takes the omitted optional parameter's default in place (`matrix.sort(m, order = order.descending)` sorts column 0 descending, `m.submatrix(to_column = 1)` keeps every row, `a.fill(7.0, index_to = 1)` fills from 0). A keyword that names no parameter, a parameter given twice (by position and by keyword) and a gap before a required parameter are refused with the diagnostics the namespace already reports for a call that does not bind (`matrix.<method>: wrong number of arguments`; for an array method its `unknown keyword argument`, `passed both positionally and by keyword` and `missing required argument`, the typed-method templates). A call without keywords, and an array method outside the checked table, keep their arguments as written. `matrix.fill` binds its range keywords (`from_row`, `to_row`, `from_column`, `to_column`) as it binds a positional range, which the lowering does not apply: both fill the whole matrix, as before (an approximation TradingView does not make, unverified (hold)). `tests/test_arrseg_review_fixes.py` pins each keyword form against its positional twin and runs the defaulted ones. A defaulted `submatrix` evaluates its receiver once. An index-only `add_row` / `add_col` takes any numeric index (an input, a function's result, `math.min(...)`); an argument whose type the analysis cannot resolve is told from an array by its C++ type. A bound result of `array.concat` -- `c = array.concat(a, b)`, `c = a.concat(b)` on a variable declared an array and bound once, and the `:=` reassignments of both -- keeps the unsupported-function refusal; the statement form, `matrix.concat` and a user method named `concat` are unchanged. A matrix bound to a missing history (`b = m[20]`, then `b.get(0, 0)`) raises the recorded na-matrix text (RE10053), as the history itself does; one passed on to a function still raises the engine's text. Follow-ups, unverified (hold): matrix diff/mult dimension checks, a `for ... in` over a bound na array ID, keywords on an array method outside the checked table, on `matrix.new` and on a UDT field's matrix, and the `matrix.fill` range.

`pineforge_codegen.support_checker` is the gate. Its job is to fail
loudly **before** codegen so users never get a silently miscompiled
strategy. An error raises `CompileError` (carrying every diagnostic); the
warnings and notes of a script that transpiles (support checker, then analyzer and
codegen `ctx.diagnostics` -- the codegen appends through `_codegen_warning`)
come back as `transpile_full(...)["diagnostics"]` and in `transpile_json`'s
success envelope under `diagnostics`, in the error envelope's entry format.
A note (`Level.NOTE`, since 1.5.0, raised through `SupportChecker._note`) is nonfatal and
informational. Only PF-W1505, PF-W1508, PF-W1509 and PF-W1525 to PF-W1532 are
notes, each keeping its `PF-W` code; every other diagnostic keeps its level,
the other visual-only and display-only ones included (for example PF-W1078,
PF-W1502, PF-W1506, PF-W1507, PF-W1552). A `PF-E` code is an error; a
`PF-W` code can be a warning or a note, so read its declared severity.

Checked settings string defaults and options use only known C++ string literals
from the existing builtin lowering, never inert visual integer codes. Only the
`currency.*` and `format.*` members inventoried in `NAME_ECHO_STRING_MEMBERS`
may publish their own names, matching the body's existing lowering; unlisted
members remain unsupported even when the body echoes their names. An unknown
string default or option marks the
input `supported=false` and publishes no choices; its unavailable default is
empty. Transpile-time input manifests reuse that descriptor's `supported`
boolean and string defaults/options; source defaults/choices and enum choices
are explicit, while enum defaults retain their member-name spelling. A typed
number or bool input publishes its default, bounds and `options=[...]` numbers
where the descriptor's C++ is a plain literal
(`checked_settings._numeric_setting_value`: a sign, a named constant the
codegen inlined, a folded `timestamp("...")`); what the receipt computes at run
time stays unpublished and is named in `KNOWN_LIMITS` of
`tests/test_input_metadata_receipt.py`, which pins every other field of every
input against the compiled receipt. A representable string default survives an
unsupported option. Legacy getters/setters and generated strategy execution
stay unchanged.

Generated run stops use `codegen/run_stops.py`'s optional
`PINEFORGE_HAS_RUN_FAILURE_CODES_V1` shims. Coded helpers receive only
compile-time request provenance and closed metadata words, never computed
symbols or the English as metadata; the fallback keeps the original throws.
`runtime.error` passes positional and named `message` arguments (an omitted
message stays empty), and `str.tonumber` evaluates its argument outside the
numeric parser's narrow catches so a run stop propagates. Run wrappers preserve
an inner exception's code; a legacy setter's first failure latches its text and
`setting_rejected` identity for both batch and native execution.

Array-history wrappers implement the same `na_stop` / `history_stop` traits
as vectors: missing array or bound matrix references report
`pine_na_reference`, and historical mutation reports `pine_array_error`.
A legacy history-element assignment outside the array reports
`pine_array_error` with reason `index_out_of_bounds` and no method. All keep
their original English on engines without coded stops. `array.sort`'s `order`
and `indexof` / `unshift`'s `value` keywords bind like their positional twins;
a missing array-template argument is a located wrong-argument refusal, not
an internal `IndexError`. `tests/test_arrseg_coded_run_stops.py` checks both
macro paths, every nullable-array trait and native `run_json` envelopes.

A change must never make a script that transpiles and compiles today fail
to transpile. A lowering that produces a value different from TradingView on
TV-valid input is a defect: fix it with the correct lowering; never keep it
with a warning.

The one exception to this rule is a located refusal: a form PineForge cannot
yet lower correctly may be refused with an error that names its source
location, instead of being lowered with a wrong value.

This exception covers only constructs PineForge refuses today. A form that compiles today keeps compiling: if its lowering is approximate, that is recorded as a defect and fixed by the correct lowering. A wrong value is never kept behind a warning, and such a form is never newly refused as unproven. A located refusal is allowed only as a labelled temporary fallback for one exact proven shape, listed as a compile gap.

The emission invariant (`AGENTS.md#emission-invariant`) states this rule for every emission path. The notes in this file describe existing behavior: a documented approximation or unsupported fallback is an implementation gap, not an exception to the invariant.

Input defaults use the input family's Pine type and qualifier contract.
An explicit `const color` carrier with a proven initializer supplies its
packed value to the getter and settings descriptor before `on_bar`; the
manifest reads that descriptor. `codegen/constant_values.py` resolves lexical
bindings on the support checker's AST, after `rename_block_locals`, using
the existing bounded scalar and color evaluators. Reassigned, persistent and
inferred carriers remain compile gaps; an initializer alone cannot prove
the value at a later call. The proof applies in every statement context,
including function bodies and switch arms. Existing direct builders keep
their lowering and metadata unless their arguments read proven const
carriers; those use the same packed proof. Static input initialization uses
`_render_input_value`, as statement reads and settings descriptors do, so
it cannot read an uninitialized carrier member in place of that proof.

If the required evidence and value checks are unavailable for a shape, the
existing located PF-E1006 is retained as a PineForge limitation and is listed
as a compile gap. A located refusal of a spelling TradingView rejects follows
its general grammar, type and qualifier rule.

The taxonomy:


| Bucket                           | What                                                                 |
| -------------------------------- | -------------------------------------------------------------------- |
| `HARD_REJECT_FUNC`               | Calls with no PineForge semantics at all (e.g. `request.seed`; `request.currency_rate` is not one: it has no feed, so it translates and stops the run where it is evaluated, its arguments first, a skipped branch evaluating nothing). |
| `HARD_REJECT_NAMESPACE`          | Whole-namespace rejects — currently EMPTY (the old `ticker.*` blanket reject became per-function `HARD_REJECT_FUNC` entries: `ticker.{renko,kagi,linebreak,pointfigure,new,modify}`; `ticker.inherit`/`ticker.standard` pass through, `ticker.heikinashi` allowed for the chart's own symbol). |

The ERROR subset is reserved for silent mis-aliases and is currently empty. |
| `BARSTATE_APPROX_VARS` (warning) | Barstate flags PineForge approximates in batch mode.                 |
| `STRATEGY_UNSUPPORTED_PARAMS`    | Per-strategy.* call kwargs that codegen drops silently.              |
| `NOT_YET_FUNC`                   | Implementable but currently no codegen — reject loudly.              |
| `SUPPORTED_*` frozensets         | Per-namespace whitelist of names codegen knows how to emit.          |

One read with history (a `Series<T>` member) keeps the first-bar preamble only for a top-level declaration of a constant, a string literal, `na` or a bar field (`_series_var_init_keeps_preamble`, byte for byte); one in a block, whatever its initializer, reads na history until the first bar that reaches it (the preamble pushed bar 0's value: a block's `var float fc = close` held the first bar's close), and any other initializer -- a UDT field (`var int signal = direction.neutral`), a global computed before it (`var float first2 = b`), a call, `ta.*`, an input's override, a `switch` / `if` selection (the preamble's spelling of one did not compile; `tests/test_e2e_cgint5_compositions.py`) -- runs at its declaration too, the preamble pushing its na until then. | `request.security` helpers | A payload inlines the user functions and typed user methods it calls on the requested bar, under a builtin call too (`nz(f())`, `close.g()`, `nz(ta.sma(close, 3))`: the expression visitor that renders the builtin hands every user call, TA site, helper-bound name and requested-bar history back to `_build_security_expr`). Under a builtin, and for a method, only a single-expression body is inlined, every user call in it too, also through a global's value (`_security_body_is_expression`); a multi-statement one keeps the chart call and warns, because the evaluator writes its statements ahead of the payload, where a ternary arm or an `and`/`or` operand would run them on every bar. A TA site reached through several helper bindings gets one variant per binding, numbered (`_v0`, `_v1`, ...) by where each binding's value is written (`_security_variant_order_key`; the signature names nodes by `id()`, whose order is memory's; `tests/test_security_variant_order.py`). A helper called on its own result (`u(u(close))`) gets a variant per written call: the variant walk's recursion guard is keyed by the call, not the helper's name, which skipped the inner call as recursion and left it reading an undeclared base member (`tests/test_e2e_security_nested_helper_call.py`). A helper local's value is re-walked under the helper-name guard still (`_security_local_rewalks`): the evaluator reads the local's C++ variable, and entering the helper again there walked every earlier local once per read, 2**n walks over a chain of n locals. A call of a pure helper (one expression over its parameters, the requested bar's fields and literals, through operators and such calls) on arguments of that kind holds nothing a prepass collects, so the payload's walks stop at it; once its inlined text is 256 characters long its value is computed once where the evaluator opens (`_pf_shared_<N>_<k>`, `_security_share_pure_call`) and every reach with the same arguments reads it, where a diamond of such helpers inlined its leaf once per path (`tests/test_security_helper_diamond.py`). A payload's `bar_index` is the requested bar's, the count of requested bars before it (`_sec<N>_bar_index_`, advanced where the evaluator opens a requested slot; `bar_index[k]` k requested bars back, na before the first; `tests/test_e2e_security_bar_index.py`). A global the payload reads at an offset (`g[1]`) whose value is a user function's call or a numeric operator expression keeps its history on the requested clock: the value the payload reads as `g`, pushed once per completed requested bar where the evaluator closes (a helper inlines the read at each read of its parameter), and the payload lowers such a global once per evaluator (`g - g[1]` inlined the call at each read, which advanced its TA state once per read). The push takes the value of a read that ran, as an inline expression's history does: a read in a ternary arm, an if branch or a loop that did not run on a requested bar pushes nothing there, where TradingView's history holds every requested bar (a limit). The once-per-evaluator lowering holds within the block that emitted its locals: a later read outside a helper's if branch or loop lowers the call again, as every earlier build did at each read (it named the locals out of scope, which did not compile), except that a call with state (a TA site, a `var`, a request, a user method) whose global the payload also reads with history on the requested clock is refused where two of its lowerings can run on one requested bar, since its state would advance twice a bar (every earlier build refused that history read; one under a builtin keeps the chart's series and never counts, and the two arms of one if never run together). The builder refused the call's history ("helper call history is only supported in the payload itself") and indexed the operator expression's C++ scalar, which did not compile (`_security_global_history_value`). That history is a double (a bool's a bool), whose na reads na -- typed from the global's `int`, the first requested bar read `na<int>()` as -2147483648 and a 64-bit integer ("Epoch ints": `g = bar_index * 86400000`, or an epoch) wrapped -- and an integer slot of the evaluator (a helper's `int` local, an int tuple element) takes it narrowed na-preserving (quirk 9; an int reaching the chart's double still reads `na<int>()` as a number, as on main). Only a read lowered on the requested clock is so: one under a builtin (`nz(g[1], 0) / 2`) keeps the chart's int series and main's lowering, and a string global's history there is refused, as every earlier build refused it (`tests/test_e2e_cgint7_compositions.py`). A `request.security` of Heikin-Ashi bars inside the payload reads the requested context's Heikin-Ashi bars on TradingView, which the evaluator does not build: evaluating it stops the run (`_security_nested_heikinashi_request`), so a selection that never takes it (`useHA ? request.security(ticker.heikinashi(syminfo.tickerid), timeframe.period, close) : close` at its default) runs on the requested bars, where rendering the call read the chart's own request. An `int` / `float` cast whose argument reads a helper's parameter or local (a TA length `int(math.round(_len / 2.0))`) is the builder's own where the TA constructors are planned: the expression visitor rendered the name as an unknown variable. `tests/test_security_global_history.py` replays TradingView's tapes (`fixtures/tail_a_tv`). A global under a builtin call (`nz(s)`) is re-evaluated on the requested bar as a bare payload global is, when the expression map holds it and it is neither replayed state nor a per-run value (`_security_fallback_owns_global`); its history there (`nz(s[1])`) keeps the chart's series and warns (`tests/test_e2e_security_global_under_builtin.py`). When extending codegen with a new Pine builtin: add to the corresponding
`SUPPORTED_*` set (or hard-reject) in `support_checker.py`, register its
signature in `signatures.py`, then wire the dispatch in
`analyzer/call_handlers.py` and `codegen/visit_call.py` (or the
namespace-specific visitor module). The cross-namespace official-surface
test will fail at PR time if you forget any of these steps.
